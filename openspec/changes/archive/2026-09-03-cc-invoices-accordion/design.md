# Technical Design: Credit Cards Invoices Accordion

## Architecture
This change is purely on the frontend layer. We are modifying `CreditCards.tsx` to handle the transactions fetching and grouping locally.
The API `/credit-cards/:id/transactions?all=true` provides all transactions for a card along with their `invoice_id`, `invoice_month`, `invoice_year`, and `invoice_status`.

## State Changes
- Remove `selectedInvoiceId` state, as we no longer select one invoice to view its transactions in a flat list.
- We will store `allTransactions` fetched via `?all=true`.
- The accordion component will use `invoices` array to render headers.
- When rendering an accordion's content, we filter `allTransactions.filter(tx => tx.invoice_id === invoice.id)` to show its items.
- Edge case: Some transactions might not have an `invoice_id` yet or are in the open/current invoice. The API logic assigns `invoice_id` explicitly or we fetch them all. Wait, `?all=true` returns all transactions with `invoice_id` (joined from `credit_card_invoices`). If `tx.invoice_id` is null, it's pending. The backend `invoices` array already has an `id` for the open period (generated by `getOrCreateInvoice`), and `?all=true` might return `invoice_id = null` for some pending. In `CreditCards.tsx` we can map `invoice_id === null` to the `is_current` invoice ID.

## Performance considerations
- Fetching `?all=true` for credit card transactions should be fast enough given typical volume, but we will add a local grouping map `transactionsByInvoice` (e.g. `Record<string, any[]>`) to avoid re-filtering the large array during every render.

## Risk Assessment
- Low risk. Only affects the presentation layer for credit cards. Backend APIs remain unchanged.
